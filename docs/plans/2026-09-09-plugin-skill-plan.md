# Plan: `playkit-js-plugin-builder`, a skill that builds production-ready PlayKit-JS plugins from one prompt

Status: **audited 2026-09-09, nothing built yet beyond scaffolding.** Every Kaltura fact below traces to `docs/plans/2026-09-09-plugin-skill-research.md` (pinned SHAs), including the Claude Code packaging facts in that doc's §11. Decisions taken during the audit are in `docs/plans/2026-09-09-audit-decisions.md`.

## 1. Problem

Kaltura's own tooling (`playkit-js-plugin-example` and its `rename-plugin` skill) renames a template. It does not help with plugin logic, tests, docs, security, or community CI/CD. The official docs are also stale in places (wrong `isValid` signature, wrong `loadMedia` timing, nonexistent `player.Event.Error`, i18n described as automatic when it is not). An agent that follows those docs produces a plugin that compiles but misbehaves.

Goal: one skill, one natural-language prompt, one plugin that is:

| Quality | Concrete meaning |
|---|---|
| Compliant | Correct `BasePlugin` lifecycle, `isValid()` with no args, `super.destroy()` called, `registerPlugin` return asserted, Kaltura naming rules, errors via `Error(severity, category, code, data)` on `player.Event.Core.ERROR`. |
| Well-architected | Right branch of four, checked in this order: Unisphere consumer (feature already exists as a Unisphere runtime; thin plugin on `@playkit-js/unisphere-service`), event-bridge, component UI (`addComponent`), or side-panel UI (`ui-managers` services). Config typed and validated at the boundary. No live config references leaked. |
| Fully tested | Unit tests for logic. E2E (Playwright in community mode, Cypress in internal mode) against a pinned player build with the mock provider by default. Lifecycle tests: reset, destroy, change-media, disabled, invalid config. |
| Verified | Every phase has a check that runs and prints pass/fail. "Done" is a count that hit zero, not a self-rating. |
| Secure | Boundary validation, no `innerHTML`/`eval` on untrusted data, `postMessage` origin allow-list, only the scoped `@playkit-js/kaltura-player-js` dependency (the bare name is a known-malicious npm package), SHA-pinned Actions, least-privilege workflow permissions, lockfile, `npm audit` and OSV scan clean, no secrets in tracked files, CDN tags pinned with SRI. |
| Resilient | Never breaks playback: `isValid()` returns false instead of throwing on bad config, listeners cleaned up, async work guarded against destroy, third-party failures downgraded to RECOVERABLE errors or logs. |
| Documented | README, Diátaxis guide, working demo page, config table generated from the TypeScript interface, `ui.translations` snippet when the plugin has UI text. |
| Releasable | Semver, tag, CHANGELOG, `dist/` at tag for jsDelivr (community) or npm (internal). |

## 2. Two audiences, one skill

| | Community mode (default) | Internal mode (opt-in) |
|---|---|---|
| Who | Anyone | Kaltura employees with org access |
| Scaffold | Generated by this skill (research §9 pattern, corrected) | `playkit-js-plugin-example` cloned, renamed via its `rename-plugin` skill |
| Base import | `@playkit-js/kaltura-player-js` modular import, marked external | same |
| CI | Public GitHub Actions, SHA-pinned, `permissions: {}` then per job, Dependabot, OSV scan | Kaltura reusable workflows (`run_tests`, `run_canary`, `run_prod`) |
| E2E runner | Playwright (full WebKit) | Cypress (template and reusable workflow) |
| Build | webpack 5 + babel + api-extractor, externals `root KalturaPlayer.*` (same as template) | same |
| Secrets | none | 8 `PLAYER_*` secrets, internal registry |
| Distribution | jsDelivr from GitHub tag, `dist/` committed at release | npm via `@kaltura/kaltura-tools` |
| `kaltura` package.json field | never | as in the template |
| Docs/demo | GitHub Pages | GitHub Pages |
| Unisphere | Consume existing runtimes through `@playkit-js/unisphere-service` (public npm) or the public docs at `unisphere.kaltura.com/docs` — no internal access needed for consumption. Cannot author or deploy runtimes; that track is gated to Kaltura developers (docs: "contact Kaltura" for partnerships). | Same, plus may author a new runtime and visuals in a `unisphere-*` workspace repo and deploy it with `@unisphere/cli` (employee-only) |

Detection: `scripts/detect-mode.sh` prints `community`, `internal`, or `ambiguous`. Internal requires both `@kaltura/kaltura-tools` resolving against the operator's npm auth and push access to a `kaltura/*` repo. `ambiguous` means ask once.

```
  .claude/
    CLAUDE.md                       # repo-dev instructions, imports ../AGENTS.md (not at plugin root: strict validate)
    skills/playkit-js-plugin-builder -> ../../skills/playkit-js-plugin-builder   # dev symlink for dogfooding
  skills/playkit-js-plugin-builder/

    reference/

      services-and-ui-managers.md   # research §7; side-panel branch

      security-checklist.md         # supply chain, Trusted Types enforcement, SDK integrity, privacy, `security-review` fallback

  AGENTS.md                         # how to build this repo

  LICENSE
```

Changes from the first draft, with reasons:

- **No `commands/build-plugin.md`.** Commands are legacy. A skill is user-invocable by default and takes `$ARGUMENTS`. Two entries for one job is confusing.
- **No committed `PORTABLE_AGENTS.md`.** Skills follow the open Agent Skills standard. The flattened export stays as an optional build artifact for tools that read one file, not as a primary form.
- **`services-and-ui-managers.md` added.** Real UI plugins (transcript, cuepoints) use the services registry and `@playkit-js/ui-managers`, not raw `addComponent`. Without this file the skill can only build the simplest UI plugins.
- **`evals/` is self-owned.** `claude plugin eval` is gated ("currently in early access", CLI 2.1.266, undocumented). The harness runs the skill headless with `claude -p --plugin-dir` and grades with our own code and LLM graders, following Anthropic's develop-tests guidance: specific measurable criteria, automate grading, code-based first, LLM rubrics that reason then output `correct`/`incorrect`, volume over hand grading. The layout stays close to the gated tool's `prompt.md` + graders shape so switching later is cheap.
- **`unisphere-integration.md` added (13 reference files).** Kaltura's newest player features (video summary, Genie chat) ship as Unisphere runtimes consumed by thin plugins on `@playkit-js/unisphere-service` (research §16). Without this file the skill would rebuild features that already exist.
- **`templates/` added.** The community scaffold has to come from somewhere deterministic, not from the model's memory.
- **`CLAUDE.md` moved under `.claude/`** so `claude plugin validate --strict .` passes.
- **`ui-components.md` covers a11y**; `error-event-taxonomy.md` covers resilience. No separate files: each would be under a page.

## 4. The skill's workflow: nine phases, each with a runnable exit check

| # | Phase | Exit check (command or file, must pass) |
|---|---|---|
| 0 | Intake | A `PLAN.md` in the target repo states: plugin name (kebab-case), architecture branch, mode, config interface, events consumed and emitted, at most one open question. It also records the Unisphere check: which runtime was matched (widget id, runtime name) or the sentence "no Unisphere runtime covers this" with the source consulted (`reference/unisphere-integration.md`). Operator has seen the "building X as Y, say so if wrong" line. |
| 1 | Scaffold | `npm ci && npm run build && npm run lint && npm run type-check` exit 0 on the empty plugin. `package.json` depends on `@playkit-js/kaltura-player-js` and never on bare `kaltura-player-js` (grep check). Community: files from `templates/`. Internal: template cloned, `rename-plugin` run, `git status` clean after rename. |
| 2 | Implement | `isValid()` has no args and returns `false` on bad config (no throw). `destroy()` calls `super.destroy()`. Nested defaults merged explicitly. No `player.Event.Error`. `registerPlugin` return asserted in a test. `grep` checks for each of these are in `reference/base-plugin-api.md`. Unisphere branch: no direct import of `@unisphere/runtime-js`, no `fetchAndLoadUnisphereWorkspace` call; workspace comes only from `player.getService('unisphereService')` (grep). |
| 3 | Test | `npm test` and `npm run test:e2e` green (CI has an explicit browser-install step because npm 12 blocks install scripts). Lifecycle tests exist for: valid load, invalid config, `disable: true`, change media (`reset` + `loadMedia`), `destroy` removes listeners and UI, error path emits RECOVERABLE. UI branch: keyboard reachability and `aria-label` assertions. The e2e page sets `Content-Security-Policy: require-trusted-types-for 'script'` (enforcing) and the run fails on any `securitypolicyviolation`. UI text: a unit test asserts every `translations/<locale>.i18n.json` has the same key set as `en`, and an e2e case loads the player with `ui.locale` set to a non-`en` shipped locale and asserts the translated string renders. Unisphere branch: unit tests run against a stubbed `unisphereService` (fake `pluginManager` and `eventService`); e2e loads the real `unisphere-service` plugin with `provider.unisphereLoaderUrl` from an env var and is skipped, not failed, when the var is unset. Trusted Types check on the Unisphere e2e page is informational until research §14 closes that gap. |
| 4 | Document | README, `docs/guide.md`, `demo/index.html` exist. README states the SaaS whitelisting constraint. Config table matches the TS interface (script diff, not eyeballing). UI text present implies a generated `ui.translations` block in README covering every shipped locale plus the `ui.locale` line (script-generated from `translations/`, diffed in CI). `authoring-kaltura-docs` used when installed. |
| 5 | Secure | `security-review` run and findings closed, or fallback checklist in `reference/security-checklist.md` fully ticked. `npm audit --audit-level=high` and `osv-scanner` clean. Actions SHA-pinned. `permissions:` set per job. No secrets in tracked files. Demo and README CDN tags pinned to an exact tag with SRI. ESLint bans Trusted Types sinks (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`, `script.src`) in plugin `src/`; demo page runs under the same enforcing CSP as the e2e page. |
| 6 | Quality gate | `karen audit` green if present. Else: lint, type-check, build, unit, e2e, audit all exit 0, and `git status` clean. |
| 7 | CI/CD and release | Mode-appropriate workflow files committed and passing on a push. First tag cut. Community: `dist/` committed at tag, jsDelivr URL resolves. Internal: canary workflow green. |
| 8 | Handoff | PR open. Body states what was built, the architecture branch, what was defaulted, and the open question if any. Notes that CI green is not the merge signal; a human or Copilot review is. |

Each reference file encodes its phase's checks as commands an agent can run. No phase exits on a self-assessment.

## 5. One prompt in, defaults out

Never ask, infer from the prompt:

- Plugin name (kebab-case). Display name. Package name.
- Architecture branch (`reference/decision-tree.md`). First check: the capability already exists as a Unisphere runtime the operator can reach implies the Unisphere consumer branch. Otherwise: visible and interactive implies UI. Reacts and reports implies event-bridge. Needs a panel, tab, or overlay implies side-panel.
- Lifecycle hooks needed. Whether `ready` should delay playback (only when the plugin cannot function without an async dependency).
- Whether i18n applies (UI text present).
- Mode, when `detect-mode.sh` is not `ambiguous`.

Ask once, batched, only when wrong is expensive:

- Mode, when ambiguous.
- Whether a third-party SDK may be loaded from a CDN, and which one.
- Partner and entry ID for the demo. Default to the mock provider and flag it.

Always state the defaults back before scaffolding.

## 6. Decisions on the open questions

Recommendations from the first draft, kept, plus new ones from the audit. All are proposed defaults until the repo owner confirms.

1. **Community-first, internal opt-in.** Unchanged.
2. **jsDelivr-first, npm opt-in.** Unchanged. If npm is chosen, prefer OIDC trusted publishing over a long-lived token.
3. **One skill folder, plugin manifest on top, flattened export optional.** Replaces "ship both forms". The `skills/` folder is copyable as-is. `export-portable.sh` produces a fallback artifact, not a committed file.
4. **Lean on existing skills, documented fallback each.** Unchanged. Fallbacks live in the reference file for that phase.
5. **Four architecture branches, not two.** Side-panel plugins are the common real case and need the services registry. The Unisphere consumer branch (item 16) is checked first.
6. **Cypress uses the mock provider by default.** Live-network e2e is opt-in and needs a partner ID. Player version pinned in the test page.
7. **SHA-pinned Actions, least-privilege `permissions:`, Dependabot on.** Community scaffold ships with these. The reference community plugin (`aws-analytics`) does not, and is not copied blindly.
8. **Portable frontmatter only.** `name, description, license` plus Claude Code `argument-hint`. No `when_to_use`. Description does both jobs in under 1,024 chars.
9. **Playwright for community e2e, Cypress for internal.** Cypress WebKit is still experimental and Safari matters for a video plugin. Internal mode keeps Cypress because the template and the reusable workflow expect it. This is the one recommendation that splits the modes; confirm or pick one runner for both.
10. **Match Kaltura's build toolchain exactly** (webpack 5, babel, api-extractor, standard-version, root-global externals). No Vite or tsup in v1. The externals pattern is what keeps preact single-instance.
11. **Scoped package name enforced by lint.** The bare `kaltura-player-js` npm name has a malicious published version. This is the one place an LLM "recalling" a package name causes real harm.
12. **Multi-language i18n in v1, as a host-page contract.** playkit-js-ui loads dictionaries once at construction and has no runtime API to add them (research §6.3). So the plugin ships `translations/<locale>.i18n.json` for every locale the operator asks for (default `en` only), a script generates the `ui.translations` block for all of them, and every `withText` key has an English fallback. Tests: key-set parity across locales, one e2e run in a non-`en` locale.
13. **Trusted Types enforced, not just compatible.** The player stack has no sinks on a top-level page without prebid (research §6.6), so the e2e and demo pages run under an enforcing `require-trusted-types-for 'script'` CSP and fail on any violation. Plugin `src/` is linted for the sink list. Generated README states the plugin is Trusted Types safe and names the two upstream exceptions (iframe embed title, prebid loader).
14. **Self-owned evals, not the gated CLI.** Two layers. Intake layer: about 15 one-line prompts, run with `claude -p --plugin-dir . --json-schema`, exact-match on `{name, branch, mode}`; cheap, so it gives volume and catches decision-tree regressions. E2E layer: three full builds in a temp dir with a budget cap, graded by code (files exist, lifecycle greps, `npm run build && npm run lint && npm test` exit 0) and by an LLM rubric (reason first, then `correct`/`incorrect` per criterion). Baseline arm: same prompts without `--plugin-dir`, to show the skill's delta. Thresholds in `evals/README.md`: intake accuracy 100 percent on 3 repeats; e2e code graders 3 of 3 runs; rubric all criteria correct on at least 2 of 3 runs. Source: platform.claude.com/docs/en/test-and-evaluate/develop-tests.
15. **Marketplace publishing in v1.** Self-hosted `marketplace.json` with `source: "./"`, validated and install-tested from GitHub first. Then submit to the community marketplace `claude-community` through the Console form (research §11). The official `claude-plugins-official` list has no submission process; it needs the Kaltura Anthropic partner contact, which the owner handles. README shows the marketplace-add plus install commands.
16. **Unisphere-first.** If the requested capability already exists as a Unisphere runtime (video summary, Genie chat, or one the operator names), the plugin is a thin consumer on `@playkit-js/unisphere-service` in the `unisphere-summary` shape: `getService('unisphereService')`, `getWorkspace()`, `loadRuntime`, `initRuntime`, storage and pub-sub contracts (research §16.6). No reimplementation of the feature, panel, icon, or workspace load. When a workspace is present, Unisphere services (pub-sub, storage, user-settings, theme, logger, analytics) are preferred over hand-rolled ones. Mode split: community mode consumes existing runtimes only; internal mode may also author a runtime and its visuals (research §16.7) and deploy it with employee-only tooling. If no runtime matches, fall through to the three classic branches. Known gaps stay explicit in `PLAN.md`: runtime entitlement, production loader URL for self-hosted players, Trusted Types with the loader (research §14).

## 7. Not in v1

- Multi-plugin monorepos.
- Non-JS PlayKit SDKs.

## 8. Definition of done for v1

1. All 13 `reference/*.md` files have real content, each self-contained, each fact traceable to the research doc.
2. `templates/` produces a community scaffold that passes phase 1 on a throwaway plugin.
3. `scripts/detect-mode.sh` returns the right answer on this machine and in a clean container.
4. Dry run on four prompts: a side-panel UI plugin (chapters from cue points), an event-bridge plugin (analytics to an external endpoint), an ad-adjacent plugin (pause-overlay or companion), and a Unisphere consumer plugin ("add the AI video summary side panel"), which must resolve to `@playkit-js/unisphere-service` plus `unisphere.widget.video-summary`, not a rebuilt summary feature. Each reaches phase 8 with all checks green; the Unisphere run's live e2e may be skipped when no loader URL is available, and that is recorded.
5. `evals/` contains the intake set (with at least three prompts that must route to the Unisphere branch and three near-misses that must not) and the same four e2e cases with code graders (files, lifecycle greps, build/lint/test) and an LLM rubric for architecture choice and stated defaults.
6. `claude plugin validate --strict .` passes. `README.md` install instructions verified by a fresh `/plugin install`.
7. Repo name settled and `plugin.json` `homepage`/`repository` match.
8. i18n: the side-panel dry run (item 4) ships `en` plus one more locale, the generated `ui.translations` block covers both, and the non-`en` e2e case passes.
9. Trusted Types: the e2e and demo pages of the three classic dry runs pass under the enforcing CSP with zero violations; the sink lint rule is on in `templates/`.
10. `evals/run.sh` executed on the intake set and the four e2e cases, meeting the thresholds in `evals/README.md`, with the baseline arm showing a positive delta. Results summary committed as a dated markdown table, raw results gitignored.
11. `marketplace.json` validated and a fresh `/plugin marketplace add` + `/plugin install` tested from the GitHub repo. Submission to `claude-community` sent through the Console form. Request to the Anthropic partner contact for `claude-plugins-official` sent by the owner, or the reason it was not recorded.
